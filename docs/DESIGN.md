# 系统设计

下文记录原型架构。新增算法与数据库草稿、发布、恢复的设计见 [整改操作与测试](revision/RESULTS.md)。

## 模块和数据关系

| 模块 | 代码位置 | 职责 |
| --- | --- | --- |
| 地图和建模 | `frontend/src/scene` | 地标、宿舍、食堂和运动场生成，镜头、拾取、标签、小地图、漫游、路线绘制 |
| 页面和共享状态 | `App.vue`、`pages`、`store.js` | 路由、筛选、详情、行程、收藏、任务、后台编辑以及 API 调用 |
| 路径与校验 | `Campus.java` | 稳定编号索引，步行图构造，路线计算，场景及道路几何验证 |
| 接口和持久化 | `CampusApi.java`、`CampusStore.java` | 校园快照、个人记录、反馈、导入和版本管理 |
| 会话和权限 | `Accounts.java`、`SecurityConfig.java` | 注册、登录、退出、BCrypt、Spring Security 角色与 CSRF |

后端在单进程内使用 Spring JDBC。数据库表 `accounts` 保存用户名、密码摘要和角色，`campus_scene` 保存带修订号的单一场景文档，`personal_items` 以账号、类别、记录编号为复合主键。结构可通过 `schema.sql` 和种子文件重建。地图、收藏、保存路线、行程、导览站点和反馈都共享同一套地点编号。保存路线记录起点、终点和途经偏好，重新打开时用最新道路状态计算。

`/api/scene` 和 `/api/route` 支持游客访问，`/api/me/*` 由当前已认证的主体确定数据归属。前端提交的数据无法指定其他人的归属。管理员接口由后端角色规则保护。反馈管理员可处理，普通用户只可读取和提交本人的反馈。

## 路线算法

把每个入口、转折处和路口作为节点。每条无向边明确记录它的两个端点、开放状态和台阶属性。坐标约定 X 近似东西向、Z 近似南北向，Y 为高度。规划时从候选图排除关闭边，用户勾选避台阶时，再排除含台阶边。

每一段用 Dijkstra 和最小优先队列找最短路，松弛时记录前驱与边编号，按用户给出的途经顺序拼接并共用相邻段的入口节点。边权是两个端点的平面欧氏长度。起终点入口相同返回单点和零距离。任一段不可达时返回 422，页面提示具体失败的两处地点。距离由局部坐标估算，步行速度为 1.25 米/秒，动画采用 14 个局部单位/秒以缩短演示时间。

管理员编辑入口、位置、朝向或道路连接时，服务端检查唯一 ID、现有引用、入口距离及道路穿楼。道路端点按建筑朝向变换到其局部坐标，用线段与矩形裁剪判断是否穿过楼体。场景可保留断开的子图，导航会按当前状态报告不可达。发布前比较修订号，数据校验通过后一次替换快照。已有业务引用或已完成的导览前缀会约束删除与改序。

## 程序化建模和交互

场景从数据库快照生成，加载种子只是初次创建数据库时的步骤。综合楼专用生成函数使用基座、分层体量、带状玻璃、斜向框架和入口雨棚。宿舍和场馆使用屋顶、楼层与窗列参数，球场单独生成界线与球架。图书馆是综合楼入口标记。树木以固定随机种子在避开楼体和路网的区域分布。

窗口、树冠、树干和灯杆使用实例化批处理，同类基础几何与材质复用。阴影图只在场景或图层变化时更新。路线实体单独更新，普通选中、搜索、图层和模拟导航无需重建整座校园。相机模式切换、页面卸载会清理控制器、键盘事件、观察器、动画任务和 GPU 资源。第一人称固定视点高度与校园边界，按建筑局部矩形检测阻挡。小地图显示当前位置或环绕焦点，可以点击地点定位。

约定新增地点先选现有节点或新增入口，再添加道路。如果项目需要室内楼层导航、实际地形起伏或全量校区 POI，可扩充数据格式及模型生成函数。
